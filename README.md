# Масочная латентная диффузия: 512 → 8192 текстовых токена

Подготовлен отдельный переносимый проект на основе ветки `mdlm-prefix-block-noisy-past-512-rw128`, commit `3ff606831e48be8069cb42a2afffa666051d53fa`. Здесь находятся кодек VQ-VAE-2, блочная масочная диффузия, обучение, генерация и оценивание. Данные и веса в папку не включены.

**На этом ПК обучение, генерация и проверка модели не запускались по просьбе пользователя.** Итог статической проверки находится в `VALIDATION.md` и `static_report.json`. Команды ниже предназначены для сервера; это инструкция, а не уже выполненные эксперименты.

Длина 512 текстовых токенов соответствует 128 VQ-кодам, 8192 — 2048 кодам. Один блок содержит 16 кодов, примерно 64 текстовых токена. Текущий блок зашумляется заменой кодов на MASK; прошлые блоки подаются как контекст. При полном контексте последний блок длинного текста получает 2032 предыдущих кода. Дополнительное сжатие прошлого здесь не применяется.

Исторический `tiny_blockcausal.yaml` и настоящие веса отсутствуют. Явно восстановлены настройки DiT: размер 512, 8 слоёв, 8 голов, conditioning 128, dropout 0.1. Это новая воспроизводимая основа из выбранной ветки; совпадение с исторической обученной моделью не установлено.

## Какие изменения внесены

| Изменение | Для чего |
|---|---|
| Генерация, выбор кандидата и исправление блока работают в общем EMA/eval-контексте. | В исходной ветке после генерации возвращались обычные веса и train-режим, а отбор выполнялся уже ими. Теперь режим оценки согласован; состояние модели восстанавливается даже при исключении. |
| Исправлена нормировка оценки кандидатов; старый вариант вынесен в отдельную настройку. | Среднее по всей длине блока согласовано с обучающим masked loss. Одинаковые маски используются для всех кандидатов; случайность отбора отделена от случайности генерации. |
| PPL считается по всему тексту скользящими окнами. | Убраны усечение до 256 токенов и повторный учёт целей последнего неполного окна. Каждый целевой токен оценивается один раз, документы обрабатываются отдельно. |
| Входные целочисленные токены кодека используют выбор строки матрицы вместо большого one-hot. | Это математически эквивалентная замена, которая убирает выделение большого входного тензора. Она сама по себе не меняет степень VQ-сжатия. |
| Декодирование выполняется совместно для всей последовательности, словарная проекция — частями. | Уменьшается размер временных logits; контекст кодека сохраняется. Для обучения добавлена проверяемая на сервере экономия памяти через checkpointing последней проекции. |
| Зашумление прошлого заменяет коды только допустимыми кодами словаря; validation использует чистое прошлое. | MASK не попадает в распределение случайной подмены прошлого. Добавлена численно устойчивая формула расписания шума. |
| Документы делятся на train/validation/test до нарезки окон. | Окна остаются непрерывными внутри одного документа. Точные дубликаты удаляются; остатки, которые не помещаются в полное окно, явно считаются. |
| Сохранены optimizer, EMA, scaler, шаг и состояния RNG; проверяются данные, кодек и конфигурация. | Можно продолжать тот же запуск или явно начать новый этап с прежних весов. Несовместимый кодек не загружается молча. |
| Добавлена проверка восстановления исходного текста кодеком. | Плохой кодек может ограничивать качество даже хорошей диффузии. Выводятся исходный и восстановленный текст, token accuracy, использование кодов и опционально CE. |
| Добавлены слепые сравнения LLM-судьёй в обоих порядках A/B. | Можно оценить связность, сущности, развитие текста, повторы и язык вместе с PPL. Экспорт и сбор ответов работают офлайн, внешних запросов в проекте нет. |

Подробности адаптации сохранены в `CODEC_NOTES.md`, `CORE_NOTES.md`, `EVALUATION_NOTES.md`. Улучшение качества и скорости ещё не измерено.

## Что можно сравнить по качеству

Настройки разнесены по отдельным файлам, чтобы менять один фактор и понимать его влияние:

- `prior_baseline_512.json` — исправленная исходная методика, контекст до 112 кодов, подмена прошлого с вероятностью 0.2.
- `prior_contexts_512.json` — тот же контроль, но обучение включает промежуточные длины контекста.
- `prior_noise01_512.json` — тот же контроль, но вероятность подмены прошлого 0.1.
- `prior_8192.json` — новый этап на длинных документах с полным прошлым, разнообразными длинами контекста и checkpointing слоёв DiT.
- `sample_reference_budget.json` — 256 шагов, 8 кандидатов, 16 оценок каждого блока, исправленная нормировка; контекст до 112 кодов.
- `sample_full_context.json` — тот же бюджет с полным прошлым.
- `sample_fast.json` — 64 шага и один кандидат; предназначен для сравнения времени и качества.
- `sample_refinement.json` — дополнительное исправление 25% текущего блока. Каждый код по очереди скрывается, модель оценивает вероятность его восстановления, затем самые неуверенные позиции генерируются повторно. Остальные позиции и прошлое фиксированы. Это экспериментальная эвристика; все дополнительные вызовы включены в `refinement_nfe`.
- `sample_legacy_score.json` — отдельное сравнение старой нормировки отбора; согласованный EMA/eval-режим сохраняется.

Повторное исправление выключено по умолчанию. Оно дороже обычного сэмплирования и не является точной реализацией ReMDM. При сравнении фиксировать кодек, данные, seed, длину, batch size и все остальные настройки. Изменение batch size меняет потоки случайных чисел. Для выводов о качестве нужны несколько seed, отложенные документы и сопоставимый вычислительный бюджет.

## Подготовка на сервере

Скопировать эту папку целиком. Требуются Python 3.10+, PyTorch и NumPy. Для текстов нужны дополнительные зависимости; версия PyTorch должна поддерживать CUDA данного сервера. Проект использует одну видеокарту и накопление градиентов. Значения batch size, количества шагов и bf16 в конфигурациях — стартовые настройки, их работоспособность на A100 ещё не проверена.

Внутри папки проекта, после настройки окружения сервера:

```text
python -m pip install -e ".[text,test]"
python -m pytest --basetemp .test-tmp
```

Тесты включают маленькие искусственные модели, сохранение/продолжение обучения, PPL и полный короткий конвейер. Они предназначены для будущей проверки. Проверка только файлов без исполнения проекта доступна отдельно:

```text
python tools/static_check.py --output static_report.json
```

Датасет сейчас не выбран и не скачивается. Подготовка принимает **локальный JSONL**: одна строка — один документ с уникальным `id` и `text`. Для запуска на реальном тексте нужен локально доступный fast tokenizer, например папка `models/gpt2-tokenizer`. Конфигурации кодека рассчитаны на словарь 50257; для другого tokenizer изменить `model.vocab_size` в обоих файлах кодека. Кодек, подготовка и декодирование должны использовать один tokenizer.

```json
{"id":"document-001","text":"Полный текст одного документа..."}
```

```text
python -m masked_longtext prepare --input data/documents.jsonl --output data/tokens --tokenizer models/gpt2-tokenizer --lengths 512 8192
```

Можно передать готовые `input_ids` вместо `text` и указать `--vocab-size 50257 --tokenizer-id my-tokenizer`. В этом режиме состав и правила tokenizer нельзя проверить по входным ID; их согласованность нужно обеспечить на этапе подготовки. Для будущего декодирования сохранить соответствующий tokenizer. Код не фильтрует программные примеры и не удаляет близкие дубликаты: будущий корпус без кода нужно отобрать отдельно. FineWeb-Edu в этой реализации не исследовался.

Для длинной серии использовать одни и те же длинные документы для обоих размеров окна. Короткие документы можно включить для отдельного опыта, но тогда это меняет состав корпуса. В manifest записываются разбиение, контрольные суммы, число окон и отброшенные хвосты. Убедиться, что на обеих длинах есть train и validation; небольшая выборка может не дать validation при hash-разбиении.

## Порядок 512 → 8192

Сначала обучить и проверить кодек на 512:

```text
python -m masked_longtext train-codec --data data/tokens --config configs/codec_512.json --output runs/codec512 --device cuda
python -m masked_longtext reconstruct --data data/tokens --codec runs/codec512/best.pt --output samples/reconstruction512 --tokenizer models/gpt2-tokenizer --text-tokens 512 --with-loss
```

Для первого короткого пилота можно кодировать только 512 этим кодеком, обучить prior и сгенерировать текст. Его результаты сохранять как отдельный пилот.

```text
python -m masked_longtext encode --data data/tokens --codec runs/codec512/best.pt --output data/codes-pilot --lengths 512 --device cuda
python -m masked_longtext train-prior --data data/codes-pilot --config configs/prior_baseline_512.json --output runs/prior-pilot512 --device cuda
python -m masked_longtext sample --checkpoint runs/prior-pilot512/best.pt --codec runs/codec512/best.pt --config configs/sample_reference_budget.json --output samples/pilot512 --tokenizer models/gpt2-tokenizer --text-tokens 512 --num-samples 20 --device cuda
```

Для сопоставимой серии на 512 и 8192 сначала получить **окончательный кодек**, который умеет восстанавливать длинные тексты, проверить его на обеих длинах и заморозить:

```text
python -m masked_longtext train-codec --data data/tokens --config configs/codec_8192.json --output runs/codec8192 --init runs/codec512/best.pt --device cuda
python -m masked_longtext reconstruct --data data/tokens --codec runs/codec8192/best.pt --output samples/final-codec512 --tokenizer models/gpt2-tokenizer --text-tokens 512 --with-loss
python -m masked_longtext reconstruct --data data/tokens --codec runs/codec8192/best.pt --output samples/final-codec8192 --tokenizer models/gpt2-tokenizer --text-tokens 8192 --with-loss
python -m masked_longtext encode --data data/tokens --codec runs/codec8192/best.pt --output data/codes-final --lengths 512 8192 --device cuda
```

Затем вновь обучить короткий prior уже на **кодах окончательного кодека**, сравнить варианты на 512 и продолжить выбранный prior на 8192:

```text
python -m masked_longtext train-prior --data data/codes-final --config configs/prior_baseline_512.json --output runs/prior512 --device cuda
python -m masked_longtext sample --checkpoint runs/prior512/best.pt --codec runs/codec8192/best.pt --config configs/sample_reference_budget.json --output samples/final512 --tokenizer models/gpt2-tokenizer --text-tokens 512 --num-samples 20 --device cuda
python -m masked_longtext train-prior --data data/codes-final --config configs/prior_8192.json --output runs/prior8192 --init runs/prior512/best.pt --device cuda
python -m masked_longtext sample --checkpoint runs/prior8192/best.pt --codec runs/codec8192/best.pt --config configs/sample_full_context.json --output samples/final8192 --tokenizer models/gpt2-tokenizer --text-tokens 8192 --num-samples 20 --device cuda
```

Если выбран другой короткий prior, заменить путь `--init` на его checkpoint. **После изменения кодека индексы VQ могут означать другое**, поэтому перенос prior между двумя разными кодеками запрещён. Нельзя просто дообучить кодек и продолжить prior на новых кодах. Альтернатива — оставить короткий кодек замороженным, если проверка его восстановления на 8192 удовлетворительна; тогда адаптация кодека и повторное короткое обучение не нужны.

`--resume runs/.../last.pt` продолжает тот же запуск с optimizer, EMA и RNG; настройки, данные и версия кода должны совпадать. `--init runs/.../best.pt` начинает новый этап с новым optimizer и расписанием; для prior берёт EMA исходного checkpoint, если она есть. Это правильный режим при переходе 512 → 8192. `best.pt` выбирается по validation loss, не по LLM-судье. Старые Lightning-файлы и Git LFS-указатели загрузчик не принимает как новые checkpoints.

## Оценка результата

`samples.jsonl` содержит VQ-коды, восстановленные токены и текст при наличии tokenizer. `generation.json` сохраняет конфигурацию, seed, checksum весов/кодека, число вызовов модели для генерации, отбора и исправления, время декодирования и пиковую память. NFE считает вызовы на batch; это нужно учитывать при сравнении batch size. Записанное время включает декодирование и запись результата, исключает загрузку весов. Для научного сравнения скорости отдельно фиксировать оборудование, precision, прогрев и повторные измерения.

Локальные повторы и разнообразие без дополнительной языковой модели:

```text
python -m masked_longtext evaluate --input samples/final512/samples.jsonl --output samples/final512/repetition.json
```

PPL с уже установленной локальной causal LM:

```text
python -m masked_longtext evaluate --input samples/final8192/samples.jsonl --output samples/final8192/evaluation.json --model models/ppl-evaluator --context-window 1024 --stride 512 --device cuda
```

PPL — средняя неожиданность токенов для конкретной внешней модели. Корректная нормировка убирает простую зависимость от числа токенов, но длина меняет состав текста, повторы и доступный контекст оценивания. Поэтому 512 и 8192 оценивать отдельными группами с одним evaluator/tokenizer и окнами; вместе с общей PPL смотреть потери по позициям, повторы и качество полной последовательности. Более низкая PPL сама по себе не доказывает лучшую связность длинного текста.

Для сравнения двух вариантов одинаковой длины и одинаковых ID:

```text
python -m masked_longtext judge-prepare --a samples/final512/samples.jsonl --b samples/variant512/samples.jsonl --output samples/judge512 --text-tokens 512
```

Это создаёт `packets.jsonl` с полными текстами A/B и B/A и локальный `mapping.json`. Судье передавать только `packets.jsonl`; схема ответа и критерии включены в сообщения. Имена моделей и PPL скрыты. Без реального tokenizer судьи бюджет контекста отмечается как непроверенный. Для строгой проверки добавить `--judge-tokenizer models/judge-tokenizer --context-budget <его_лимит> --response-reserve 2048`; требуется настоящий chat template. Текст при нехватке бюджета не обрезается. Внешние вызовы пользователь запускает отдельно.

Ответы сохранять как JSONL `{"packet_id":"...","response":{...},"metadata":{"model":"...","revision":"..."}}`, затем:

```text
python -m masked_longtext judge-collect --packets samples/judge512 --responses samples/judge512/responses.jsonl --output samples/judge512/results.json
```

Сбор проверяет структуру, диапазоны оценок, цитаты и целостность текстов. Пропуски, неверные ответы, несогласие при смене порядка и неопределённые результаты остаются в отчёте. Победа засчитывается при согласии двух порядков. Судья требует отдельной проверки на человеческой разметке; автоматический score не заменяет её.

## Границы реализации

Полное прошлое пересчитывается при изменении текущего блока: исходное attention двунаправленное, поэтому простой кэш прошлого менял бы модель. `ddpm_cache` кэширует предсказания для неизменившегося состояния, а не KV прошлого. Очень длинный контекст остаётся дорогим; фактическую скорость и память нужно измерить.

Не реализованы DDP, beam search, точный ReMDM, специальная память для далёкого прошлого и обучение на прошлом, сгенерированном самой моделью. Текущий проект — подготовленная масочная основа для последующего сравнения с симплексной диффузией; преимущество одного процесса над другим ещё не установлено.
